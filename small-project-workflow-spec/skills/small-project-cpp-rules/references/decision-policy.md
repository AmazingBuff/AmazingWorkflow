## 权威顺序

本文件嵌入小项目 workflow 后，权威顺序受 workflow 总规范约束；以下顺序不得解释为用户要求可以推翻正确性、安全、法律、平台或兼容性硬约束。

对每个具体问题单独判断，不用一条全局偏好覆盖整个仓库：

1. 正确性、安全、法律、平台和兼容性硬约束。
2. 用户明确要求。
3. 仓库内贡献指南、构建配置、格式化器、静态检查器、CI，以及已发布公共 API/ABI、序列化格式和持久化数据。
4. 当前模块相邻、重复且一致的第一方实现。
5. 仓库内其他模块反复出现的稳定模式。
6. 本 skill 的绿地默认值。

规则只在适用范围内生效。应用层惯例不能自动覆盖底层 ABI，测试代码惯例也不能自动覆盖生产接口。

## 完整度判断

同一权威层级的候选方案冲突时，先比较完整度：

- 是否覆盖声明、实现、调用方和销毁路径。
- 是否处理正常、失败、空值、边界和并发场景。
- 是否在受支持平台和构建类型中成立。
- 是否有测试、CI、静态检查或真实消费方验证。
- 是否能解释依赖、所有权和错误传播。
- 是否是重复模式，而非单个文件中的偶然写法。

完整度明显更高的方案优先。只有完整度相当时，才用修改时间作为决胜条件；较新不等于更正确。

## 新旧规则冲突

- 新的正式配置优先于旧的非正式写法，但只用于新增或触及的代码。
- 新实现若缺少调用方、测试或失败处理，不因时间更新而覆盖完整旧实现。
- 旧公共接口若仍被消费，先保持兼容，再通过适配层或版本化迁移。
- 不从删除一半的重构、TODO、stub 或未接入路径推断新规范。
- 无法确认时，选择修改面更小且可回退的方案，并记录假设。

## 既有项目

先探测再修改：

1. 找到目标定义、调用方、测试和 CI 命令。
2. 读取 `.clang-format`、`.clang-tidy`、`.editorconfig`、CMake presets 和包管理配置。
3. 在受影响模块抽取至少两个相邻第一方样本。
4. 区分必须保持的接口兼容与可局部改善的实现细节。
5. 只格式化或重命名本次触及的最小范围。

若局部惯例与本 skill 默认值不同，局部惯例优先，除非它违反明确要求、正确性或安全性。

## 绿地项目

没有现有约束时：

- 选择能满足当前需求的最小目录和目标集合。
- 明确语言标准、支持平台、库类型、依赖获取和测试入口。
- 从本 skill 选择一套一致默认值，不同时引入多个风格变体。
- 在首次提交中加入格式化、静态检查和可重复构建配置。
- 仅为当前需要创建目录、接口、扩展点和自动化。

## 排除错误证据

不要从以下内容推断项目规范：

- vendored、submodule、SDK、生成代码和机械 API 表。
- build、install、cache、IDE 临时文件和编译数据库。
- 已复制的示例、基准输入、资源文件和许可证文本。
- 单次 workaround、废弃代码、注释掉的实现、拼写错误和未完成分支。
- 与当前任务无关的语言、平台或工具链目录。

这些内容可以证明依赖或边界存在，但不能证明第一方命名、格式或抽象偏好。

## 迁移边界

- 不把局部功能修改扩大为全仓格式化或目录重排。
- 不在没有兼容计划时重命名公共符号、目标、安装路径或配置键。
- 将机械迁移和行为修改拆成独立变更，便于审查和回退。
- 批量迁移前先在一个代表模块验证构建、测试和调用方影响。
- 无法一次完成时，保持新旧边界清晰，不创建第三套过渡风格。
