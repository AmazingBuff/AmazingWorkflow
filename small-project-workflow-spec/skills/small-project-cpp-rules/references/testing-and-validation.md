# 测试与验证

本文件只为 workflow 的强模型测试规划者提供 C++ 检查项，并指导执行 Agent 运行已经批准的测试包。它不决定测试时机、通过标准或门禁；这些由通过当前 Harness 原生 loader 加载的 `small-project-test-plan` 统一管理。实现阶段只运行任务包允许的最窄构建、静态检查或 smoke，不得据此自行宣称 `G6 TEST_PASS`。

## 目录

- 验证策略
- 测试设计
- 外部边界
- 构建矩阵
- 完成报告

## 验证策略

按风险选择最窄且足够的验证：

1. 纯实现细节修改：相关单元测试和目标构建。
2. 公共接口修改：所有调用方、接口测试和兼容性检查。
3. CMake/依赖修改：重新 configure、受影响目标构建和最小消费测试。
4. 平台适配修改：对应平台或明确等价的 contract test。
5. 所有权、并发或内存修改：生命周期测试，并在可用时运行 sanitizer。
6. Bug 修复：先建立能复现旧行为的回归测试，再验证修复。

先使用项目已有脚本、presets 和 CI 命令，不另造平行验证入口。

## 测试设计

- 测试公共行为、可观察状态和契约，不绑定私有调用顺序。
- 覆盖核心路径、边界值、失败路径和资源释放。
- 一个测试只表达一个主要行为，命名说明场景和预期。
- 使用参数化测试覆盖同一规则的输入矩阵。
- 单元测试必须可重复，不依赖执行顺序、真实时间或外部网络。
- 示例和 benchmark 不代替断言明确的测试。
- 不为达到覆盖率数字测试无行为的 getter 或编译器生成代码。

## 外部边界

- 只在文件系统、时钟、随机数、网络、进程、数据库或可替换适配器边界使用 mock/fake。
- 优先使用轻量 fake 或 in-memory 实现，避免脆弱的调用次数断言。
- contract test 应让多个实现运行同一组行为用例。
- 无法自动化的硬件或系统行为提供可重复 smoke test 和清晰的人工步骤。
- 测试夹具拥有并清理自身资源，不把状态泄漏到其他测试。

## 构建矩阵

变更涉及下列维度时扩展验证：

- Debug 与 Release 行为可能不同。
- 静态库与共享库导出不同。
- 多个编译器或标准库受支持。
- 多平台源选择或 capability detection 改变。
- 可选 feature flag 改变公共头或依赖。
- 安装包需要被外部项目消费。

不要求为局部无关修改运行完整矩阵；说明选择了哪些代表配置以及原因。

## 完成报告

最终报告包含：

- 修改了什么可观察行为或工程约束。
- 关键架构、所有权和兼容性决策。
- 实际运行的格式化、静态检查、configure、build 和 test 命令。
- 每条命令的结果。
- 因环境、平台、SDK 或权限未验证的部分。
- 已知风险和最小后续步骤。

不把“命令存在”写成“已通过”，不省略失败后采用的替代验证。
