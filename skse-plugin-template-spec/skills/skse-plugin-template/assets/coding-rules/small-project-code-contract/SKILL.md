# Small Project Code Contract

> 组合适配版：改编自 small-project-workflow-spec 的同名规范（基线 `5fb6ec0`），作为 skse-plugin-template 的编码规范组件随套件分发；仅调整编排词汇，代码规则未变。来源与同步策略见套件 README.md。

这是所有实现语言共同遵守的工程契约；语言规范只补充语言特有规则。

## 规则优先级

1. 正确性、安全、平台和兼容性硬约束；
2. 用户明确要求；
3. 仓库正式配置、CI、已发布 API/ABI 和数据格式；
4. 当前模块稳定的第一方模式；
5. 语言规范的绿地默认值；
6. 通用偏好。

低优先级规则不得推翻高优先级规则，也不得借功能改动批量重排或格式化无关代码。

## 模块与文件

按真实职责或能力组织目录，明确依赖方向。小项目不为了模板制造空目录、无调用者的接口或只有转发的层；出现第二个稳定职责、独立构建/测试边界或可替换能力时再拆分。

## 函数设计

只有至少满足一项时才拆函数：

- 在多个位置复用；
- 表达可被独立替换的功能；
- 隔离外部副作用、资源或并发边界；
- 形成可独立理解和测试的稳定步骤。

不按行数机械拆分，不为单一路径预建抽象。便利入口应统一转发到一个权威实现，避免复制转换、规则或校验。

## 输入验证

每次跨越新的不可信边界时，完成一次解析、类型或范围检查与规范化，并尽快转换为可信领域值。CLI、UI、API、文件、网络、数据库、插件、FFI 和可复用库的 public API 都可能是边界。

可信域内部函数依赖清晰前置条件，不得重复对同一用户输入做 `if/throw/return` 校验。以下不算冗余输入验证：程序员不变量断言、内存和生命周期安全、并发或 ABI 检查、运行时状态检查，以及来自新外部边界的数据检查。

## 依赖与变更范围

第三方库仅在显著降低复杂度、提高正确性或提供成熟能力时推荐。方案确认前记录用途、替代方案、版本策略、许可证、体积和平台影响；实现 Agent 不得自行新增依赖。

只修改实现契约（implementation contract）授权的范围。公共接口、数据格式、构建方式、依赖或架构需要变化时，停止实现并经 Planner 与用户确认新契约修订版。

## 完成检查

确认模块边界真实、内部无重复输入验证、函数拆分有理由、依赖已批准、无无关改动，并按对应语言规范执行最窄构建与静态检查。
